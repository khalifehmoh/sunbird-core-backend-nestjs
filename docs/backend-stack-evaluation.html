Backend Stack Evaluation — Spring Boot vs NestJS

Sunbird healthcare backend, scoped to the upcoming patient management and ICU modules, with FHIR, HL7 device integration, and event-driven processing on the roadmap. Two engineers on the project.

DECISION
Build on NestJS, with Medplum as the internal FHIR engine behind a single front door.

With two engineers, any component only one person can maintain has a bus factor of exactly one. Java components would have at most one maintainer; NestJS components have two. Every gap that pointed toward Spring now has a TypeScript-native answer — and at this team size, operate managed, pre-built services rather than building or self-hosting infrastructure.

How it fits together

Medplum's server cannot merge into the NestJS process — different framework, different schema, its own release cycle. It runs as a second service behind a single front door: same docker-compose.yml, one login, one API surface. No caller ever needs to know it is there.

Arrows are internal calls. Only the NestJS API is externally reachable; the Agent makes outbound connections only, so no inbound firewall rule is needed at the hospital.

What does not shrink with better tooling: compliance sign-off on patient-data-touching changes, and physical change-control access to on-prem Agent installs. Both are gates by design, not capability gaps.

Build order

  1. Foundation: Medplum in docker-compose.yml, auth seam (Sunbird JWT as the single source of truth), one patient screen via @medplum/react proxied under /api/v1 — validates the three riskiest seams at once.
  2. Patient management: CRUD-heavy, lowest technical risk; exercises Task-based workflows and Bots.
  3. ICU module last: highest technical risk (real-time load, alarm logic, device bridging) — lands on a proven foundation, after the event-loop load spike has run.

Validate before deep investment

  • Event-driven spike: one clinical reaction built twice — as a Medplum Bot on a Subscription and as a BullMQ job — to establish which pattern fits which class of event (no Kafka)
  • Add Medplum to docker-compose, proxy it under /api/v1, and build one patient screen with @medplum/react on the existing Mantine theme
  • ICU real-time spike: realistic bed count and sample rate, with a deliberately CPU-heavy alarm step included
  • Device bridge spike: one Medplum Agent endpoint plus the minimal Bot that acknowledges and maps a real device's messages
  • Auth seam: make Sunbird's existing JWT the single source of truth and have Medplum trust it — before real patient data flows
  • Workflow spike: one care pathway as FHIR Task transitions driven by Bots; only repeat it in Temporal if compensation-on-failure is genuinely needed
